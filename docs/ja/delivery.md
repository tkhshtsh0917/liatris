# イベントの永続配送

[English](../delivery.md)

## ブラウザと受信側

コレクターの `queue` に `createQueuedDelivery` のインスタンスを渡します。プロファイルとそのハッシュに加え、`sendBatch` に `createHttpBatchDelivery(endpoint)` で作った送信処理を指定します。収集の前にコレクターへ同意を渡します。`queued` は IndexedDB への保存完了、直接送信モードの `sent` は設定した配送処理の完了を示します。

キューの上限はオリジン・テナント・アプリケーションごとに512件です。最後の64件分は `result_impression`、`impression` 以外のレコード向けに予約され、送信可能なレコードの中でもこれらを優先します。上限に達すると新しいレコードを拒否します。配送対象は24時間で期限切れになり、キューの動作時に削除されます。一時的に失敗したレコードは同じ内容とイベント ID で再送し、`Retry-After` の待ち時間は上限付きで反映します。トークンはリクエストごとに取得し、キューには格納しません。同意、再接続、タブの表示状態の変化で再送を再開します。

導入例の `parallelBatches: 2` は、同じキューから別々のイベントを含む二つのバッチを同時に送ります。二つの応答はどちらが先に届く場合もあります。独自の送信処理では既定で一度に一つのバッチを送ります。送信中のバッチがなければ、保存したクリックはすぐに送信を開始できます。

同時に届くイベントは最大32件まで同じ IndexedDB トランザクションにまとめます。各イベントの `queued` は、そのトランザクションが確定した後に返します。 同時に届く活動のセッション判定は採集順に行い、最後のセッション状態を一度だけ保存します。保存前に同意の世代を確認します。

タブは IndexedDB 上の同意の世代、セッション、キューを共有します。同意を撤回すると、現在の世代を読み出して開いているタブに通知した後、セッションを含まない新しい世代とキューの削除待ちを記録します。読み出しに失敗した場合、撤回元で有効だった世代が分かっていれば、その世代を使って他のタブに通知します。同じ世代への通知を受けると、進行中の配送と初期化途中の同意の有効化を停止します。通知を受けたタブで再同意したときに IndexedDB に撤回前の世代が残っていれば、古いキューを削除して新しい世代を開始してから配送を再開します。

撤回の記録を保存した後、二つ目のトランザクションで送信待ちイベントと削除待ちの記録を消します。削除が失敗しても、削除待ちの記録は再読み込み後に残ります。再同意で送信を開始するには、先にこの削除が完了する必要があります。遅れて実行された処理が IndexedDB を更新する前にも世代を確認します。導入先では失敗した撤回の再試行用オブジェクトを保存でき、再読み込み後も新しい世代に影響させずに再試行できます。収集サービスにすでに達したリクエストは受理済みの場合があります。受理済みデータはサーバー側で削除します。[導入ガイド](integration.md)

ストレージの更新では既存のセッションと送信待ちイベントを引き継ぎます。更新後にキューを開くには、削除待ちの記録に対応した SDK が必要です。

バッチは `application/vnd.liatris.batch+json` の JSON 配列で送ります。1リクエスト最大32件・128 KiB、各レコード最大32 KiB です。有効なバッチリクエストには HTTP 200 と、送信された `event_id` ごとに一つの受領結果を返します。イベント ID の重複など、バッチの構造が無効な場合は HTTP 400 を返します。

| ステータス | キューの処理 |
| --- | --- |
| `accepted` | 受信側が保存を確認したため、削除します。 |
| `rejected` | 恒久的な失敗として、削除します。 |
| `retry` | 一時的な失敗として、再送のために保持します。 |

受領結果が欠けている、重複している、または解釈できない場合は、バッチ全体を再送します。リファレンス受信側はバッチの有効なイベントを一つの SQLite トランザクションで保存してから受領を返します。内容の競合はイベント単位で拒否します。ストレージ障害で保存が取り消された場合、そのトランザクションの対象はすべて再送します。同一テナント・アプリケーションで同じ内容を再送した場合は同じ1件として受理し、イベント ID が同じで内容が異なる場合は拒否します。単件用の `application/json` も引き続き利用でき、受理時は HTTP 204、同じ ID で内容が異なる場合は HTTP 409 を返します。データベースのパスは `LIATRIS_DB` で指定でき、デモの既定値は `liatris-demo.sqlite` です。本番データを保存する際は保存期間と削除の方針を決め、データベースファイルへのアクセスを制限します。

## ストリーミング先への転送契約

導入先が低遅延のストリーミング基盤を選び、サーバー側のアダプターで接続します。アダプターは送信待ちテーブルから確定済みのイベントを読み出し、UBI エンベロープと `event_id` を保ちます。転送先が受理を確認したイベントだけを転送済みにし、バッチの一部だけが失敗したときも、受理を確認できなかったイベントは再送できるように保持します。転送先ごとの上限とエラー処理はアダプターで扱います。ブラウザと受信 API の受領契約は配送先を問わず共通です。

転送先がイベントを受理してから送信待ちテーブルに反映するまでの間にプロセスが停止すると、再配送されることがあります。下流の読み取り側は収集範囲内の `event_id` で重複を排除できます。

## 接続例としての Amazon Kinesis Data Streams

一つの SQLite の送信待ちテーブルとストリームに対して、一つの転送ワーカーを動かします。`LIATRIS_KINESIS_STREAM`、`AWS_REGION` と、サーバー側の AWS 認証情報プロバイダーを設定します。ワーカーは `LIATRIS_DB` を使い、テナントとアプリケーションを選ぶ TOML プロファイルは `LIATRIS_PROFILE` で指定できます。ローカル検証で HTTP の Kinesis エンドポイントを指定した場合は HTTP/1.1 を使います。 キューが空のときは250 msおきに確認し、転送先の障害時は指数バックオフを使います。

```sh
npm run forward:kinesis
npm run test:kinesis
```

Compose のテストは、リファレンス HTTP 受信側へ単件とバッチで送信します。同じイベント ID を両方のリクエストで送り、Moto から読み戻した2件のエンベロープを照合します。バッチの一部だけが成功する場合は単体テストで検証します。IAM ロールは対象ストリームへの書き込みに限定し、本番の IAM ポリシーとサービスの制限は AWS 上で検証します。[Kinesis の IAM 文書](https://docs.aws.amazon.com/streams/latest/dev/controlling-access.html)

## 検証

ブラウザ配送の検証は `mise exec -- npx playwright install chromium firefox webkit` で Chromium、Firefox、WebKit を入れて、`mise exec -- npm run test:browser` を実行します。受領応答の消失、再読み込みをまたぐ保持、別タブからの同意撤回、露出集中時の優先配送、部分的な受領、旧キューの移行に加え、オフラインからの復帰、429 に従う再送、保存容量エラーからの回復、タブの表示状態が戻ったときの配送再開を確認します。ページと SDK を読み込んでいれば最初のイベントをオフラインでキューに保存できることと、v0.2.0 で保存したセッションを再利用できることも確認します。

## 露出が集中したときの性能

v0.1.0 と v0.2.0 を、3ブラウザ各3回のローカル試験で比較しました。同時に250件のカード露出が発生し、HTTP 応答に40 msの人工遅延を加えた条件では、試行ごとの p95 の中央値がキュー保存で97 msから19 ms、受領で384 msから206 msに短縮しました。両版とも露出欠損はゼロでした。同じ条件でクリック発生から受領までの中央値は72 msから83 msに増えました。

ローカルの SQLite 受信試験では、1リクエスト最大32件、HTTP 並列8で約1.66万件/秒から約4.36万件/秒に増えました。認証はテスト用の検証器を使いました。[ローカルベンチマークの実行方法](../../benchmarks/README.ja.md)
